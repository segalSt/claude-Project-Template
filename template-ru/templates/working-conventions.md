# Общие рабочие конвенции

Переиспользуемый файл — не привязан к конкретному проекту, копируется в
другие репозитории как есть. Правила и паттерны того, как ассистенту
работать в проекте, а не про сам проект. Проектный контекстный файл
(аналог `tegExpertPrompt.md`) должен указывать только отличия/уточнения,
не повторять текст этих правил.

**Справочный файл, не обязателен к полной загрузке каждую сессию.**
Обязательный минимум критичных гейтов (что реально блокирует правку/статус
«Сделано») — в `guardrails.md`, его перечитывать всегда. Сюда — обращаться
по необходимости, когда нужна деталь/обоснование/исключение конкретного
правила за пределами того, что покрывает `guardrails.md`, а не грузить файл
целиком по умолчанию.

## Изменения и разрешения

- Изменения в файлах — только после явного разрешения пользователя, если
  проект это оговорил (уточнить один раз в начале, не предполагать по
  умолчанию ни "да", ни "нет"). Полная формулировка (распространяется на
  ЛЮБОЙ артефакт проекта — код, спеку, мокапы, контекстный файл) —
  `templates/actualization-rules.md`, пункт 7.
- **Обсуждение — не разрешение.** Разбор задачи на шаги, уточняющие
  вопросы, оценка/анализ текста запроса — не разрешение начинать правки —
  см. `templates/actualization-rules.md`, правило 7. Не дублируется здесь.
- **Без предположений — сначала проверить источник (необходимо).** Прежде чем
  утверждать что-либо о коде, данных или поведении как ответ, прочитать реальный
  источник (код, XML, логи). Если нужен источник, которого нет, — **ВСЕГДА** спросить
  пользователя; только если подтверждено, что источника нет, можно заявить с явной
  пометкой `[assumption:]`. Никогда не выдавать догадку за проверенный ответ.
- **Единственная команда, означающая разрешение приступить к работе —
  `-start <номер>`** — вся механика (гейт, номер строки, что считается/не
  считается разрешением) описана в `commands.md`. Не дублируется здесь.
- Нетривиальные архитектурные/дизайн-решения — сначала явный вопрос с
  вариантами и рекомендацией, дождаться явного согласия, не реализовывать
  и не переделывать по кругу (реализовал → обсудили снова → выкинули —
  дороже, чем спросить заранее).
- **Предлагаемые правки — всегда unified diff** (единый формат для всех
  изменений): для ЛЮБОГО файла, каждый раз: полное имя файла (+ метод, если это
  исходный код); `@@ lines N-M @@` локализует каждый ханк с номерами строк; не
  менее 10 строк исходного кода вокруг с обеих сторон (щедрее для нетривиальных
  правок); `-` старое / `+` новое.
- **Проверять применённые вручную правки перед продолжением (строго).** После
  подтверждения «готово» — перечитать исходник и провалидировать по КОДУ (не по
  номерам строк): (a) правка верна; (b) кодировка файла цела (объявленная в
  проекте); (c) конвенции документации кода (блок истории изменений + строка,
  маркеры задачи, маркер версии); (d) ни одна существующая конвенция не пропущена.
  Не продолжать, пока всё не пройдено.
- **Правило перечитывания контекста после сжатия** (обязательное, не
  рекомендация) — вынесено в `templates/actualization-rules.md`, пункт 4.
  Не дублируется здесь.

## Git и коммиты

- Своего рабочего shell/git может не быть в конкретной сессии — не
  предполагать, что доступ появился в новой сессии, проверять по факту
  каждый раз.
- Перед подготовкой commit-сообщения — спросить у пользователя текущий
  `git status`/`git diff`, если нет прямого доступа; не сочинять список
  изменений по памяти о ходе разговора.
- Commit-сообщение — короткий заголовок + при необходимости
  сгруппированные по файлам пункты, без лишних пояснений, если проект не
  указал другой формат явно.
- См. также команду `-commit` в `commands.md`.

## "Живой" план работ и актуализация артефактов

- Правила про обязательную синхронизацию плана, лог расхождений
  (`errors.md`), ссылку на шаг при обсуждении, каталог тестов и
  проактивное сообщение об устаревших данных/файлах (с вопросом
  "актуализировать сейчас или задачей в конец шага") — единый файл
  **`templates/actualization-rules.md`**. Не дублируются здесь.
- При любом изменении плана — явно указывать в чате, какой шаг(и)
  изменился (номер и название), сразу в том же ответе, где сделана
  правка — не оставлять пользователя гадать, куда попало изменение.
- После изменения тестовых данных/логики — напоминать прогнать тесты и
  прислать вывод, если нет рабочего доступа к тестовому раннеру.

## Ограничения инструментов (мои, не проектные)

- Нет инструмента удаления файлов в типичной сессии — если файл нужно
  убрать из репозитория, помечать `DEPRECATED` в комментарии/шапке файла
  и явно просить пользователя удалить вручную, не оставлять это
  неотслеженным где-то в памяти разговора.
- Нет инструмента переименования/перемещения — "перенос" файла на
  практике означает скопировать содержимое в новое место (Read+Write);
  оригинал остаётся и тоже требует ручного удаления пользователем.
- Если нет рабочего shell — не мочь запускать сборку/тесты/git самому;
  просить пользователя прогнать команду и прислать вывод, не имитировать
  результат.
- Дефолтный инструмент правок/записи может перекодировать файл в UTF-8. Если
  проект объявил обязательную кодировку (см. интервью в `new-project-setup.md`/
  `migration.md`) — править такие файлы только кодо-безопасным способом (или
  отдать пользователю сниппеты) и проверять кодировку после.
- Если проект на setup указал, что место записи файлов ассистентом отличается от
  рабочей копии, из которой билдят/коммитят (отдельная билд-машина, песочница и
  т.п.), — отдавать ВСЕ правки кода диффами/сниппетами для ручного применения и
  проверять по git diff / выводу тестов пользователя, а не по своим чтениям.
  (По умолчанию: прямые правки допустимы.)

## Визуальные материалы

- Мокапы/скетчи экранов показывать по одному (один рендер за раз),
  дожидаться реакции пользователя, не выкладывать несколько сразу в одном
  ответе.

## Уровень усилий (model effort)

- При заведении задачи/шага (`-new`) и при составлении/оценке плана —
  прикидывать нужный effort: **medium** — дефолт (обычные экраны,
  code-behind, логика + тесты, документация, мелкие фиксы); **high** —
  нативный interop, рискованные спайки, крупные архитектурные развилки
  (несколько вариантов/большое решение).
- High-задачи/шаги помечать в плане (напр. раздел «Уровень усилий»).
- Если задача, к которой приступаем, оценена как high — ПЕРЕД выполнением
  явно попросить пользователя переключить режим на high; не начинать
  high-задачу на medium.
- Ассистент НЕ переключает effort сам — нет ни инструмента, ни доступа;
  сменить уровень может только пользователь в клиенте. Поэтому «попросить
  переключить» — единственный путь.

## Ручное QA по чек-листу

- Прогон ручного QA по чек-листу (например по экрану) — спрашивать строго
  по ОДНОМУ пункту за раз, не списком (вопрос с вариантами). Каждый вопрос
  ОБЯЗАН содержать: (1) что проверяем; (2) пошаговую инструкцию
  воспроизведения в приложении; (3) ожидаемый результат. Варианты:
  «Прошло» / «Не прошло» / «Пропустить». Не переходить к следующему пункту
  без ответа по текущему.
- Прошедшие — список в чате. Непрошедшие (баги приложения) — сразу в
  проектный файл находок QA (напр. `docs/qa-findings.md`): id, экран,
  симптом, ожидаемое поведение, статус Open/Fixed. НЕ в `errors.md` (тот
  про рассинхрон документации с кодом, а не про баги приложения).
- По завершении чек-листа — сводка (прошло/не прошло/пропущено), затем
  пройти по файлу находок: по каждому Open-багу спросить у пользователя, в
  какой шаг плана завести его задачей, и выполнить `-new` (форма «задача в
  шаге»), текст задачи — из описания бага.
- После починки бага — отметить его в файле находок как Fixed.

## Экономия токенов

Вынесено в **`templates/token-economy.md`** (строго) — краткость вывода,
дисциплина размера файлов, подбор модели, делегирование сабагентам, длина
сессии. Здесь не дублируется; менять там.

## Язык

- Указать явно (в проектном контекстном файле) язык кода/комментариев/
  commit-сообщений и отдельно — язык общения с пользователем в чате, если
  они отличаются. Не путать эти два языковых контура.
