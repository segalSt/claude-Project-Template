# Команды ассистента

Переиспользуемый файл — не привязан к конкретному проекту, можно
копировать в другие репозитории как есть. Короткие команды, которые
пользователь вводит прямо в чат; ассистент должен их распознавать в любой
сессии, где подключён этот файл.

Для команд, которым нужен проектный контекст (`-QA`), сам проектный файл
(например, `tegExpertPrompt.md` или аналог) должен явно указывать, где
лежит план/список шагов проекта (обычно `plan.md` или `docs/plan.md`).

**Раскладка плана (масштабируемая, см. `plan-template.md`).** Команды ниже
работают при ЛЮБОЙ из двух раскладок:
- **Монолит** (маленький проект): все шаги — прямо в `plan.md`, у каждого
  внутри свои `### Задачи` и `### Ручное QA`.
- **Split** (большой проект, после порога): `plan.md` = мета + `## Индекс
  шагов` (№, название, статус уровня шага, ссылка); тело каждого шага — в
  отдельном файле `plan/step-<N>.md` (закоммиченные — `plan/archive/step-<N>.md`),
  внутри — `### Задачи` + дизайн + `### Ручное QA`.

Правило источника: команда всегда берёт данные из того места, где сейчас
живёт шаг — раздел `### Задачи` / `### Ручное QA` в `plan.md` (монолит) или
в файле шага (split). Проектный контекстный файл фиксирует, какая раскладка
сейчас используется.

**Терминология:** план состоит из **шагов** (единица планирования
верхнего уровня, обычно один коммит). Внутри шага — **задачи** (в чате
показываются таблицей с номером строки, см. правило ниже) — конкретные
пункты работы внутри шага. `-start <номер>` — номер именно задачи из
последней показанной таблицы, не номер шага.

---

_Соглашение: команда - токен с одним дефисом (`-plan`); её аргументы/флаги - с **двойным дефисом** (`--s`, `--fix`). Позиционные аргументы (числа/текст) без дефиса._

- **`-commands`** — показать в чате список всех команд из этого файла
  (название + одна строка описания), ничего не выполнять.
  - **`--a`** — создать НОВУЮ команду: спросить у пользователя её текст
    (название) и возможные аргументы, добавить определение в этот файл
    (`commands.md`), затем актуализировать контекстный файл проекта
    (список команд) и обе языковые копии шаблона (RU + EN-зеркало по карте
    токенов). Только после явного текста от пользователя.
  - **`--full`** — показать таблицу всех команд и их аргументов с полными
    описаниями (команда · аргумент · описание); в отличие от голого `-commands` (название + одна строка).

- **`-QA [номер]`** — вывести в чат чек-лист "Ручное QA" для шага плана
  проекта. Источник — раздел `### Ручное QA` шага (в `plan.md` при
  монолите или в файле шага при split-раскладке).
  - С параметром (например `-QA 3`, `-QA 0.5`) — взять шаг с этим номером
    напрямую, без дальнейшего определения.
  - Без параметра — ТЕКУЩИЙ шаг, определяется в таком порядке: (1) явно
    назван пользователем в этом же или недавнем сообщении; (2) шаг,
    описанный как текущий/активный в проектном контекстном файле; (3)
    если оба неприменимы — первый сверху вниз шаг в плане, у которого нет
    пометки "готово"/"закоммичено" в статусе.
  - Если номер не существует в плане, или без параметра всё равно
    неоднозначно — переспросить у пользователя, какой шаг имеется в виду,
    а не гадать.

- **`-plan`** — показать список всех шагов плана проекта с вычисленным
  статусом каждого (`new`/`in progress`/`done`/`committed` — из пометки в
  заголовке шага, а при её отсутствии — из общего контекста; если
  неочевидно, пометить вопросом в выводе, не придумывать). Формат по
  умолчанию (без параметров) — таблица: № шага, название, статус, одна
  строка сути, без разбивки на задачи. Источник для голого `-plan` при
  split-раскладке — `## Индекс шагов` в `plan.md`; при монолите — заголовки
  шагов в `plan.md`.

  Параметры (комбинируются):
  - **`--s <номер>`** — план только по этому шагу: статус шага + таблица
    его задач (раздел `### Задачи` шага — в `plan.md` или в файле шага).
  - **`--a`** — то же самое, но для АКТИВНОГО (текущего) шага — тот же
    порядок определения, что у `-QA` без параметра / у контекста,
    выставленного `-start --step <номер>`.
  - **`--m <модуль>`** — дополнительный фильтр по модулю/форме (столбец
    "Модуль/форма" в таблице задач) — оставляет только задачи с этим
    модулем. Без `--s`/`--a` рядом — фильтрует все задачи по всем шагам
    сразу.
  - **`--c`** — короткий вид: список шагов БЕЗ разбивки на задачи, даже
    если указаны `--s`/`--a` — `--c` всегда побеждает.
  - **`--hide-done`** — скрыть все законченные задачи из таблицы (строки, чей
    статус начинается с "Сделано"/аналога "готово" для этого проекта).
    Остальные статусы (не начато, в работе, отменено и т.п.) остаются
    видимыми. Комбинируется с `--s`/`--a`/`--m`; с `--c` не имеет смысла.
  - Если шаг с указанным `--s <номер>` не существует в плане —
    переспросить, не гадать.

- **`-tbd <текст>`** (to be discussed) — зафиксировать тему, которую нужно
  обсудить ПЕРЕД тем, как что-либо по ней применять:
  1. Сразу добавить строку в план проекта (`plan.md`/аналог), раздел
     "## TBD (обсудить перед применением)" — текст, статус `Open`.
     Ничего не реализовывать и не менять в плане/спеке/коде по существу
     темы на этом шаге.
  2. Начать обсуждение в чате — статус меняется на `Discussing`. Вести его
     как раунд `/grilling` (вызвать инструмент Skill с "grilling"):
     вопросы с рекомендациями, весь фронтир за раз, дождаться ответов — а
     не неструктурированную переписку туда-сюда. Если тема затрагивает
     новую предметную терминологию — вызвать вместе с ним ещё и
     "domain-modeling" (как в `/grill-with-docs`), чтобы решённые термины
     попали в `CONTEXT.md`.
  3. По итогам обсуждения — явное решение пользователя:
     - принято → статус `Accepted`, тема переносится в план отдельным
       шагом/правкой, в таблице указывается номер этого шага;
     - отклонено → статус `Rejected`, запись остаётся в таблице (не
       удаляется, для истории), реализация не начинается.
  Как и везде — обсуждение само по себе не разрешение начинать работу,
  нужно отдельная команда `-start <номер>` после того, как статус стал
  `Accepted` (см. ниже).

- **`-start <номер>`** — начать выполнять задачу с этим номером из
  таблицы ТЕКУЩЕГО шага/раздела плана (последняя показанная в чате
  таблица статуса).
  - Это **единственная** команда, означающая разрешение приступить к
    работе. Любая другая формулировка — "начни", "делай", "исполни",
    "давай", согласие по смыслу, простое упоминание номера шага без
    команды и т.п. — разрешением НЕ считается, даже если по контексту
    кажется очевидным.
  - Номер — номер СТРОКИ (задачи) из последней показанной таблицы, не
    номер шага плана и не номер TBD.
  - Если номер не соответствует ни одной задаче последней показанной
    таблицы, или неясно, какая именно таблица имеется в виду (показано
    несколько таблиц подряд) — переспросить, не начинать работу.
  - После выполнения — обновить статус этой задачи в плане и явно
    указать в чате, какой шаг(и) плана изменился.

- **`-start --step <номер>`** — переключиться на работу с шагом `<номер>`,
  НЕ начиная никакую конкретную задачу:
  1. Показать в чате таблицу задач этого шага из его раздела `### Задачи`
     (в `plan.md` при монолите или в файле шага при split-раскладке).
  2. Пометить этот шаг как ТЕКУЩИЙ — используется дальше по умолчанию
     для `-QA` без параметра и как контекст для голого `-start <номер>`
     (номер задачи теперь берётся из ЭТОЙ таблицы, пока не переключились
     на другой шаг).
  3. Ничего не реализовывать — чисто навигационная команда, разрешения на
     работу не даёт (так же, как `-tbd`/обсуждение). Разрешение на
     конкретную задачу — по-прежнему только `-start <номер>` (без
     `--step`) после того, как таблица показана.
  - Если шаг с таким номером не существует в плане — переспросить, не
    гадать.

- **`-start --day`** — начать новый рабочий день / сессию (обратное к `-park`):
  перечитать контекст (файл правил + точка входа + `plan.md` + активный шаг;
  если путь к контексту неизвестен/недоступен — сначала спросить), убедиться,
  что все non-avoidable reminders активны, затем показать короткий бриф
  (что сделано + текущий статус). Только загрузка/навигация - НЕ разрешает правки.

- **Правила про номер строки в таблицах и про окно/модуль в задачах** —
  вынесены в `templates/actualization-rules.md`, пункты 5-6. Не
  дублируются здесь.

- **`-commit`** (также распознавать старую формулировку "создай коммит",
  если она где-то проскочит по привычке) — перед тем как готовить текст
  commit-сообщения:
  1. Спросить у пользователя текущий `git status` / `git diff`, если у
     ассистента нет рабочего доступа к git в этой сессии (не
     предполагать, что доступ есть — проверять по факту каждый раз).
  2. Готовить текст коммита строго по тому, что реально изменилось (по
     выводу пользователя), не сочинять по памяти о ходе разговора.
  3. Стиль сообщения — короткий заголовок + при необходимости
     сгруппированные по файлам пункты, без лишних пояснений, если проект
     не указал другой формат явно.

- **`-new`** — создать новую запись в плане проекта: шаг или задачу. После
  получения команды СНАЧАЛА спросить у пользователя текст (задачи/шага), и
  только потом сохранить в план. Как и `-tbd`/`-start --step`, `-new` НЕ
  разрешает реализацию — лишь заводит запись; выполнение задачи по-прежнему
  только по `-start <номер>`. После записи — указать, какой шаг изменился.

  Аргументы:
  - **`--t`** — новая ЗАДАЧА в АКТИВНОМ (текущем) шаге. Номер: если у шага
    есть завершающий QA-таск, новая задача вставляется ПЕРЕД ним (берёт его
    номер, QA сдвигается на +1 — QA всегда последний); иначе — следующий по
    порядку номер.
  - **`--s`** — новый ШАГ. Спросить номер, название и суть; при монолите —
    добавить секцию `## Шаг N` в `plan.md` (с `### Задачи`/`### Ручное QA`);
    при split-раскладке — создать файл `plan/step-<N>.md` и строку в
    `## Индекс шагов`.
  - **`--s <номер> --t`** — новая задача в шаге `<номер>` (а не в активном);
    правило номера то же; этот шаг считается текущим контекстом.

  При заведении также прикинуть нужный effort (medium — дефолт; high —
  нативный interop/рискованный спайк/крупная архитектурная развилка); если
  high — отметить в задаче и предупредить, что перед `-start` нужно
  переключить режим на high (см. `working-conventions.md`).

- **`-drift`** — проверить контекстные файлы проекта на дрейф (план / файлы
  шагов / спека / контекстный файл / devHistory между собой и против кода);
  сообщить о расхождениях, не чинить молча (см. `templates/actualization-rules.md`).
  - **`--fix`** → починить найденные расхождения. Если проверка `-drift` не была
    только что запущена — сначала запустить её, затем подготовить правки и
    показать статус. Правки контекстных файлов подчиняются гейту `-start`
    (показываются диффом, применяются только по `-start`).

- **`-park`** — подготовка к закрытию (конец сессии):
  1. сохранить все открытые контекстные задачи;
  2. синхронизировать файлы (контекст в соответствии с кодом/состоянием);
  3. запустить `-drift`;
  4. показать текущий статус экономии токенов;
  5. если проблем не найдено — показать дневной бриф + прощальное сообщение.
  Правки контекста подчиняются гейту `-start`.
