# New Project Setup — бутстрап нового проекта

Промпт для ассистента (Claude). Использовать как первое сообщение в
новом чате, когда нужно начать новый проект со структурой контекста,
отработанной здесь (tagsExpert): `commands.md`, `guardrails.md`,
`working-conventions.md`, `actualization-rules.md`, `docs/SPEC.md`, `docs/plan.md`, `docs/errors.md`,
`docs/qa-findings.md`, `docs/devHistory.md`, точка входа
`<ИмяПроекта>Prompt.md`. Шаблоны всех
этих файлов — в `templates/`, копия той же структуры, что уже
используется в tagsExpert.

Ни один шаг не выполняется молча - каждый требует ответа/подтверждения
пользователя там, где указано.

**Прежде всего — прочитать `README.md`** (назначение и модель работы). Ключевое:
шаблон ведёт ОДИН проект/версию за раз через фазы **спека → план → реализация
→ проверка → завершение**; каждая фаза = 1+ заданий; `plan.md` — план текущей
версии (её шаги-фазы), сделанное и прошлые версии уходят в `devHistory.md`, не
в план. Шаги 1-4 ниже — это и есть фазы «спека» и «план».

---

## Шаг -1 — не слишком ли это большая задача для одной сессии?

Этот шаблон (шаги 0-4) предполагает, что проект/версия достаточно
небольшие, чтобы спека уместилась в одной сессии — прогрилить, написать
`docs/SPEC.md`, готово. Если идея вместо этого большая и туманная
(затрагивает несколько подсистем, многоквартальная инициатива, много
сквозных решений ещё не видно) — это предположение не работает: сначала
использовать `/wayfinder` (навык mattpocock) вместо этого. Он строит карту
тикетов-решений в трекере задач (нужен предварительный запуск
`/setup-matt-pocock-skills`) и разрешает их по одному — каждый тикет типа
"grilling" на этой карте вызывает те же два навыка, что и
`/grill-with-docs`, но уровнем ниже. Возвращаться к шагу 0 здесь, как
только тикет (или вся карта, если она окажется маленькой) сузится до
масштаба одного проекта/версии.

Если неясно, что применимо — спросить пользователя, а не гадать; проект
такого небольшого масштаба по умолчанию сразу переходит к шагу 0.

## Шаг 0 — проверить результат прошлого `/grill-with-docs`, или предложить его запустить

Прежде чем проводить интервью, проверить, существуют ли уже `CONTEXT.md`
и/или `docs/adr/` в корне проекта.

**Если они есть** (например, из сессии `/grill-with-docs`, проведённой до
этого бутстрапа) — это **источник ответов**, а не то, что стоит
игнорировать в пользу нового интервью:

- Прочитать их полностью.
- На шаге 1 пропускать любой вопрос, на который уже есть ответ там
  (elevator pitch, стек, модель данных/терминология, нефункциональные
  ограничения и т.п.) — озвучить найденное вместо того, чтобы спрашивать.
  Спрашивать только про пункты 1-9 ниже, на которые действительно ещё нет
  ответа.
- На шаге 4 использовать их как источник для черновика `docs/SPEC.md` (см.
  шаг 4).

**Если их нет** — явно предложить сначала запустить `/grill-with-docs`, до
шага 1 — рекомендуется для любого проекта с реальными дизайн-/domain-
вопросами; по-настоящему тривиальный проект может сразу перейти к
интервью, если пользователь предпочитает. Дождаться выбора пользователя,
не предполагать. Если согласны — запустить, затем обработать результат по
абзацу выше, прежде чем переходить к шагу 1.

Это не заменяет шаги 1-4 — CONTEXT.md/ADR питают `docs/SPEC.md` здесь, тот
же файл, тот же шаблон, то же место. Это отдельная вещь от `/to-spec`
(другой навык mattpocock): тот — для отдельных фич/тикетов, когда
реализация уже идёт, и публикует в трекер задач этого репозитория в своём
собственном шаблоне — он не пишет `docs/SPEC.md` и не является частью
бутстрапа нового проекта. Не вызывать его здесь.

## Шаг 1 — интервью о проекте

Задать вопросы (не заваливать всё одним сообщением - использовать
инструмент вопросов, если доступен, или разбить на 2-3 сообщения).
Пропускать любой пункт, на который уже есть ответ в `CONTEXT.md`/`docs/adr`
по шагу 0 — озвучить найденный ответ вместо того, чтобы спрашивать:

1. Название проекта.
2. Одна-две фразы: что это и зачем (elevator pitch).
3. Технологии/стек (язык, фреймворк, платформа) - или "ещё не решено,
   обсудим".
4. Где будет жить проект (путь на диске / репозиторий) - новый код или
   уже существующий.
5. Язык кода/комментариев/коммитов vs. язык общения в чате, если
   отличаются.
6. Будут ли автотесты - нужен ли `docs/tests-catalog.csv`.
7. Политика правок: менять файлы сразу или только после явного
   разрешения на каждое изменение.
8. Кодировка файлов: сохранять конкретную кодировку (легаси, напр. кодовая
   страница Windows-1255) или UTF-8/Unicode подходит (дефолтный инструмент
   правок может перекодировать файлы).
9. Паттерн применения правок: ассистент пишет прямо в рабочую копию, из которой
   вы билдите/коммитите, или изменения отдаются диффами/сниппетами для ручного
   применения (напр. билд-машина — отдельный/закрытый бокс)? — от этого зависит
   прямая правка vs сниппеты и как проверять (свои чтения vs ваш git diff / тесты).

Не переходить к шагу 2, пока не получены ответы хотя бы на пункты 1-4.

## Шаг 2 — создать структуру папок и файлов контекста

```
<project-root>/
  <ИмяПроекта>Prompt.md      <- из templates/context-file-template.md
  commands.md                 <- копия шаблона, без изменений
  guardrails.md               <- копия шаблона, без изменений
  working-conventions.md      <- копия шаблона, без изменений
  token-economy.md            <- копия шаблона, без изменений
  actualization-rules.md      <- копия шаблона, без изменений
  docs/
    SPEC.md                    <- из templates/SPEC-template.md, разделы 1/3/4
                                  предзаполнены ответами шага 1, остальное TODO
    plan.md                    <- из templates/plan-template.md (без шагов - шаги 0+
                                  добавляются после того как SPEC согласован)
    errors.md                  <- из templates/errors.md, пустая таблица
    qa-findings.md             <- из templates/qa-findings.md, пустая таблица
    devHistory.md              <- из templates/devHistory.md, без записей -
                                  первая запись ("Сессия 1") добавляется в конце
                                  ЭТОЙ сессии, когда бутстрап закончен
    README.md                  <- короткая точка входа для git-хостинга (опционально)
    tests-catalog.csv           <- только если пункт 6 шага 1 - "да"
```

Новый проект стартует с **монолитного** `plan.md` (все шаги внутри него).
Когда план разрастётся сверх порога (см. `plan-template.md`) — он
разносится в **split**-раскладку: `plan.md` = `## Индекс шагов`, тело
каждого шага в `docs/plan/step-<N>.md` (закоммиченные — `docs/plan/archive/`).
Разбиение делается позже отдельной операцией (см. `migration.md`), на
старте папку `docs/plan/` не создавать.

Перед созданием - показать пользователю этот список путей и спросить
подтверждение (может захотеть другие имена/расположение).

## Шаг 3 — предложить скопировать готовые файлы контекста

Явно спросить пользователя, копировать ли как есть (без содержательных
правок на этом шаге):
- `commands.md` (команды `-commands`/`-QA`/`-commit`);
- `guardrails.md` (быстрая справка — жёсткие правила, читать первым каждую
  сессию и после сжатия контекста);
- `working-conventions.md` (общие рабочие конвенции);
- `token-economy.md` (правила экономии токенов);

- `docs/errors.md` (пустой шаблон таблицы расхождений);
- `docs/qa-findings.md` (пустой шаблон таблицы QA-находок);
- `docs/devHistory.md` (пустой журнал сессий);
- `docs/plan.md` (шаблон с мета-правилами, без шагов).

Дождаться подтверждения, не копировать молча.

## Шаг 4 — написать SPEC проекта вместе с пользователем

`docs/SPEC.md` — не имитировать содержимое по догадке.

- **Если на шаге 0 найдены `CONTEXT.md`/`docs/adr/`**: составить черновик
  разделов `templates/SPEC-template.md` прямо из них, а не проводить
  интервью с нуля — Назначение из вводного описания CONTEXT.md, Модель
  данных из его раздела Language/глоссария, Основная логика и
  Нефункциональные требования из принятых решений и ADR, Окружение
  разработки из любого ADR про стек. Показать пользователю полный
  черновик, раздел за разделом, и получить явное подтверждение по каждому
  — та же планка, что и для ответа на интервью, просто стартуя с
  черновика вместо пустого раздела. Всё, что осталось открытым после
  grill-сессии (или не ложится чисто в раздел спеки) — всё равно через
  настоящий вопрос с вариантами и рекомендацией, как ниже.
- **Иначе**: провести пользователя по разделам `templates/SPEC-template.md`
  как структурированное интервью: назначение → модель данных → основная
  логика → хранение → (UI, если применимо) → нефункциональные требования
  → окружение разработки.

Правила по ходу интервью (из `working-conventions.md`):
- Каждый нетривиальный дизайн-вопрос — явный вопрос с вариантами и
  рекомендацией, не выбирать самому.
- Раздел "Открытые вопросы" спеки не должен быть пуст на старте — туда
  складывается всё, что ещё не решено; пункт уходит оттуда, только когда
  пользователь явно согласился с решением.
- Спека не считается готовой к разработке, пока пользователь явно не
  подтвердил её (не обязательно "Approval" целиком — хотя бы устно
  "ок, поехали").

## После шага 4

1. Заполнить точку входа (`<ИмяПроекта>Prompt.md`): "Что это"/"Стек"/
   "Прямо сейчас" (статус: "инициализация, спека согласована, план ещё
   не расписан" или аналогично).
2. Вместе с пользователем построить `docs/plan.md` как план ТЕКУЩЕЙ версии —
   фазы-шаги под согласованную спеку (см. модель в `README.md`): типично
   реализация → проверка → завершение (спека/план уже пройдены на шагах 1-4).
   Каждый шаг = 1+ заданий. В план идут ТОЛЬКО шаги текущей версии; сделанное
   и прошлые версии — в `devHistory.md`, не в план. `-plan` затем показывает
   именно эти шаги.
3. Добавить первую запись в `docs/devHistory.md` ("Сессия 1") - конспект
   всего, что сделано в этой бутстрап-сессии (интервью → структура →
   SPEC → первые шаги плана). Раздел "Прямо сейчас" точки входа —
   ссылка на эту запись, не пересказ.
4. Спросить, нужен ли git-репозиторий с нуля (`git init`, первый коммит,
   пуш) - см. пример команд в `plan-template.md`/в готовом `docs/plan.md`
   этого репозитория (tagsExpert) как референс, если нужно.
5. Предложить запустить `/setup-matt-pocock-skills` прямо сейчас, не
   выходя из этой бутстрап-сессии — он настраивает трекер задач этого
   репозитория (GitHub/GitLab/локальный `.scratch/`) и триаж-лейблы,
   разовая настройка. Сделать это здесь — значит, всё будет готово до
   первой фичи/бага. Не обязательно для завершения бутстрапа; пользователь
   может отложить.

Когда начнётся реализация и появятся отдельные фичи/баги как отдельные
единицы работы, `/to-spec` (навык mattpocock) — инструмент для них: он
синтезирует и публикует спеку для одного такого инкремента в трекер
задач, настроенный выше. Это параллельный, более поздний инструмент для
спек по тикетам, не замена `docs/SPEC.md` выше — не вызывать его во время
бутстрапа.

## Шаг 5 — уборка: перенести в `context/`, удалить инструментарий бутстрапа

Когда бутстрап по-настоящему закончен (шаги 1-4 + пункты 1-5 «После шага 4»
все пройдены — спека согласована, план построен, точка входа заполнена, у
`devHistory.md` есть Сессия 1, git инициализирован если нужен,
`/setup-matt-pocock-skills` запущен если нужен) — проекту больше не нужна
собственная локальная копия инструментария бутстрапа, и его рабочие файлы
не обязаны валяться россыпью в корне. **Сначала копировать, потом
удалять, никогда наоборот** — убедиться, что каждый целевой файл существует
и читается корректно, прежде чем удалять его источник.

1. Создать `context/` в корне проекта.
2. Перенести в `context/` (просто переименование/перемещение, содержимое не
   меняется): `commands.md`, `guardrails.md`, `working-conventions.md`,
   `token-economy.md`, `actualization-rules.md`, `CONTEXT.md` (если использовался
   `/grill-with-docs`), собственный `README.md` этого набора шаблонов
   («назначение и модель работы» — отдельно от проектного
   `docs/README.md` для git-хостинга, если он есть, тот тоже переносится,
   но под своим именем), и всю папку `docs/` целиком (так `docs/SPEC.md` →
   `context/docs/SPEC.md`, `docs/adr/` → `context/docs/adr/`,
   `docs/agents/` (если запускался `/setup-matt-pocock-skills`) →
   `context/docs/agents/` и т.д. — всё под `docs/` переносится одним блоком).
3. Когда каждый перенесённый файл подтверждён на месте под `context/` —
   удалить `new-project-setup.md`, `migration.md` и `templates/` (всю
   папку) из корня проекта. Это МЕХАНИЗМ бутстрапа, а не содержимое самого
   проекта; once бутстрап закончен — он отработал своё.
4. **Актуализировать каждую ссылку на путь** в каждом оставшемся файле
   (точка входа и всё, что теперь под `context/`), чтобы они указывали на
   новые пути относительно `context/`, а не на старые корневые. Та же
   дисциплина, что правило 9 `actualization-rules.md`, выполненная один
   раз, механически, как последнее действие бутстрапа. Не оставлять
   висячих ссылок на `templates/` или корневой файл, которого больше нет.
5. В корне проекта в итоге остаётся только точка входа
   (`<ИмяПроекта>Prompt.md`) как контент этого набора шаблонов — плюс всё,
   что нужно собственному коду/сборке проекта, и любой файл, который
   требует в корне ДРУГАЯ система, независимо от этого шаблона (например,
   `CLAUDE.md`/`AGENTS.md` для `/setup-matt-pocock-skills` — он остаётся в
   корне по конвенции ТОГО инструмента, не этого).

Этот шаг опционален, но рекомендуется, когда бутстрап действительно
закончен; его можно выполнить и позже отдельно (он не обязан идти в той
же сессии, что шаги 1-4).
