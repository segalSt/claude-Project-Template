# New Project Setup — бутстрап нового проекта

Промпт для ассистента (Claude). Использовать как первое сообщение в
новом чате, когда нужно начать новый проект со структурой контекста,
отработанной здесь (tagsExpert): `commands.md`, `working-conventions.md`,
`actualization-rules.md`, `docs/SPEC.md`, `docs/plan.md`, `docs/errors.md`,
`docs/qa-findings.md`, `docs/devHistory.md`, точка входа
`<ИмяПроекта>Prompt.md`. Шаблоны всех
этих файлов — в `templates/`, копия той же структуры, что уже
используется в tagsExpert.

Ни один шаг не выполняется молча - каждый требует ответа/подтверждения
пользователя там, где указано.

**Прежде всего — прочитать `README.md`** (назначение и модель работы). Ключевое:
шаблон ведёт ОДИН проект/версию за раз через фазы **спека → план → реализация
→ проверка → завершение**; каждая фаза = 1+ заданий; `plan.md` — план текущей
версии (её шаги-фазы), сделанное и прошлые версии уходят в `devHistory.md`, не
в план. Шаги 1-4 ниже — это и есть фазы «спека» и «план».

---

## Шаг 1 — интервью о проекте

Задать вопросы (не заваливать всё одним сообщением - использовать
инструмент вопросов, если доступен, или разбить на 2-3 сообщения):

1. Название проекта.
2. Одна-две фразы: что это и зачем (elevator pitch).
3. Технологии/стек (язык, фреймворк, платформа) - или "ещё не решено,
   обсудим".
4. Где будет жить проект (путь на диске / репозиторий) - новый код или
   уже существующий.
5. Язык кода/комментариев/коммитов vs. язык общения в чате, если
   отличаются.
6. Будут ли автотесты - нужен ли `docs/tests-catalog.csv`.
7. Политика правок: менять файлы сразу или только после явного
   разрешения на каждое изменение.
8. Кодировка файлов: сохранять конкретную кодировку (легаси, напр. кодовая
   страница Windows-1255) или UTF-8/Unicode подходит (дефолтный инструмент
   правок может перекодировать файлы).
9. Паттерн применения правок: ассистент пишет прямо в рабочую копию, из которой
   вы билдите/коммитите, или изменения отдаются диффами/сниппетами для ручного
   применения (напр. билд-машина — отдельный/закрытый бокс)? — от этого зависит
   прямая правка vs сниппеты и как проверять (свои чтения vs ваш git diff / тесты).

Не переходить к шагу 2, пока не получены ответы хотя бы на пункты 1-4.

## Шаг 2 — создать структуру папок и файлов контекста

```
<project-root>/
  <ИмяПроекта>Prompt.md      <- из templates/context-file-template.md
  commands.md                 <- копия шаблона, без изменений
  working-conventions.md      <- копия шаблона, без изменений
  token-economy.md            <- копия шаблона, без изменений
  actualization-rules.md      <- копия шаблона, без изменений
  docs/
    SPEC.md                    <- из templates/SPEC-template.md, разделы 1/3/4
                                  предзаполнены ответами шага 1, остальное TODO
    plan.md                    <- из templates/plan-template.md (без шагов - шаги 0+
                                  добавляются после того как SPEC согласован)
    errors.md                  <- из templates/errors.md, пустая таблица
    qa-findings.md             <- из templates/qa-findings.md, пустая таблица
    devHistory.md              <- из templates/devHistory.md, без записей -
                                  первая запись ("Сессия 1") добавляется в конце
                                  ЭТОЙ сессии, когда бутстрап закончен
    README.md                  <- короткая точка входа для git-хостинга (опционально)
    tests-catalog.csv           <- только если пункт 6 шага 1 - "да"
```

Новый проект стартует с **монолитного** `plan.md` (все шаги внутри него).
Когда план разрастётся сверх порога (см. `plan-template.md`) — он
разносится в **split**-раскладку: `plan.md` = `## Индекс шагов`, тело
каждого шага в `docs/plan/step-<N>.md` (закоммиченные — `docs/plan/archive/`).
Разбиение делается позже отдельной операцией (см. `migration.md`), на
старте папку `docs/plan/` не создавать.

Перед созданием - показать пользователю этот список путей и спросить
подтверждение (может захотеть другие имена/расположение).

## Шаг 3 — предложить скопировать готовые файлы контекста

Явно спросить пользователя, копировать ли как есть (без содержательных
правок на этом шаге):
- `commands.md` (команды `-команды`/`-QA`/`-коммит`);
- `working-conventions.md` (общие рабочие конвенции);
- `token-economy.md` (правила экономии токенов);
- `actualization-rules.md` (правила актуализации документации/артефактов);
- `docs/errors.md` (пустой шаблон таблицы расхождений);
- `docs/qa-findings.md` (пустой шаблон таблицы QA-находок);
- `docs/devHistory.md` (пустой журнал сессий);
- `docs/plan.md` (шаблон с мета-правилами, без шагов).

Дождаться подтверждения, не копировать молча.

## Шаг 4 — написать SPEC проекта вместе с пользователем

`docs/SPEC.md` — не имитировать содержимое по догадке. Провести
пользователя по разделам `templates/SPEC-template.md` как структурированное
интервью: назначение → модель данных → основная логика → хранение → (UI,
если применимо) → нефункциональные требования → окружение разработки.

Правила по ходу интервью (из `working-conventions.md`):
- Каждый нетривиальный дизайн-вопрос — явный вопрос с вариантами и
  рекомендацией, не выбирать самому.
- Раздел "Открытые вопросы" спеки не должен быть пуст на старте — туда
  складывается всё, что ещё не решено; пункт уходит оттуда, только когда
  пользователь явно согласился с решением.
- Спека не считается готовой к разработке, пока пользователь явно не
  подтвердил её (не обязательно "Approval" целиком — хотя бы устно
  "ок, поехали").

## После шага 4

1. Заполнить точку входа (`<ИмяПроекта>Prompt.md`): "Что это"/"Стек"/
   "Прямо сейчас" (статус: "инициализация, спека согласована, план ещё
   не расписан" или аналогично).
2. Вместе с пользователем построить `docs/plan.md` как план ТЕКУЩЕЙ версии —
   фазы-шаги под согласованную спеку (см. модель в `README.md`): типично
   реализация → проверка → завершение (спека/план уже пройдены на шагах 1-4).
   Каждый шаг = 1+ заданий. В план идут ТОЛЬКО шаги текущей версии; сделанное
   и прошлые версии — в `devHistory.md`, не в план. `-plan` затем показывает
   именно эти шаги.
3. Добавить первую запись в `docs/devHistory.md` ("Сессия 1") - конспект
   всего, что сделано в этой бутстрап-сессии (интервью → структура →
   SPEC → первые шаги плана). Раздел "Прямо сейчас" точки входа —
   ссылка на эту запись, не пересказ.
4. Спросить, нужен ли git-репозиторий с нуля (`git init`, первый коммит,
   пуш) - см. пример команд в `plan-template.md`/в готовом `docs/plan.md`
   этого репозитория (tagsExpert) как референс, если нужно.
